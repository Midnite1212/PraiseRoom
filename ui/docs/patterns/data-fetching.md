# Data fetching

Reference: `src/features/songs/api.ts`, `src/routes/_app/songs/index.tsx`.

- **One `api.ts` per feature** holds the Zod schemas for its responses and the `queryOptions` factories. Components and loaders import those factories; they never build query keys inline.
- **Every request goes through `apiRequest(path, schema, options)`**, which adds the bearer token, encodes `query`, sends JSON, throws `ApiError(status)` on failure, and parses the response with the schema. Model only the fields the UI uses; Zod strips the rest.
- **Query keys** start with the feature and resource and end with the params object: `['songs', 'search', { keyword, page }]`.
- **Detail routes** load with `ensureOrNotFound(queryClient, options)` (`src/lib/ensure-or-not-found.ts`), which turns a 400 or 404 into the not-found screen, then read with `useSuspenseQuery`. Pass `{ fresh: true }` when the page edits from what it loads, so it never seeds a draft from stale cache.
- **Loaders prefetch, components read:** a route's `loader` calls `context.queryClient.ensureQueryData(options)`, and the component calls `useQuery(options)` (add `placeholderData: keepPreviousData` for paging so the old page stays visible).
- **Long lists load as you scroll, never as numbered pages.** Define the list with `infiniteQueryOptions` (`songListInfiniteQueryOptions` in `src/features/songs/api.ts`; the page number is the query's page param, not a route search param), prefetch it in the loader with `ensureInfiniteQueryData`, read it with `useInfiniteQuery`, and call `fetchNextPage` from `useNearEnd(ref, { enabled, onNear })` (`src/hooks/use-near-end.ts`) on a sentinel element after the list, so the next page loads before the end is reached. Show `LoadingStatus compact` while `isFetchingNextPage`.
- **Chrome that only displays counts** (the rail) reads the cache with `useCachedQueryData(options.queryKey)` (`src/hooks/use-cached-query-data.ts`) and is warmed by a loader's `prefetchQuery`. An observer there would be disconnected while a page suspends, cancelling the fetch that page's loader awaits.
- **Option lists the server owns** (song keys and themes: `songKeysQueryOptions`, `songThemesQueryOptions` in `src/features/songs/api.ts`) are public queries with a `z.array(z.string())` schema; never hard-code them in the UI. Read them with `useQuery(options)` where they render, and render no options (never a fallback list) until they load. They change only with a deploy, so `staleTime: Infinity` is fine.
- **Read-only POST endpoints** (the body is too large for a query string, such as `themeSuggestionsQueryOptions` in `src/features/songs/api.ts`) are still queries, never mutations: key them with the input, debounce the input with `useDebouncedValue` before it reaches the key, and gate with `enabled`.
- **Mutations** use `useMutation` with `apiRequest(..., { method: 'PUT', body })`, then `queryClient.invalidateQueries({ queryKey: [feature] })` on success, plus a toast for success and failure.
- **Errors:** client errors (4xx) are not retried (see `src/lib/query-client.ts`). Show a translated message; never render `error.message`.
- **Session:** use `Route.useRouteContext().session` inside `/_app` routes; outside them, `useQuery(sessionQueryOptions)`.
